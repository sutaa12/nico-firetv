# ソースリリースの手順

[README](../README.md) · [変更履歴](../CHANGELOG.md) · [検証状況](VALIDATION.md)

この文書は公開前のチェックリストです。
手順の追加だけでは、Release作成・署名・実機確認の完了にはなりません。

## 1. 公開候補を固定する

- 既存の未コミット変更と未追跡ファイルを確認し、公開する実変更を明示する。
- `app/build.gradle.kts` の `versionName` と `versionCode` を決める。端末に入れた版より `versionCode` を増やす。
- `CHANGELOG.md` の Unreleased を、実際に公開するバージョンと公開日に置き換える。ローカル開発日を過去の公開日として扱わない。
- 公開候補をコミットし、`.gitignore` の許可対象だけが入っていることを確認する。認証情報、端末ログ、個人パス、署名鍵、作業メモ、応募文案を含めない。

## 2. 候補コミットを検証する

候補コミットの追跡ファイルだけを別の空の作業場所に展開し、JDK 17 / Android SDK Platform 35を用意します。
既存のビルド出力や個人用 `local.properties` に依存しないことを確認します。

```sh
./gradlew --no-daemon :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleRelease
```

テスト件数、失敗・スキップ、Lintのエラー・警告、ビルド結果、環境、コミット、APKのSHA-256を記録します。
キャッシュの再利用有無と実行日も記載します。
[実機テンプレート](DEVICE_TESTING.md)で変更箇所を確認し、できなかった条件を明記します。
現行版の未実施項目を過去の別バージョンの結果で合格にしないでください。
相対リンク、第三者ライセンス、公開差分の秘密情報も確認します。

## 3. 配布範囲を決める

現状のreleaseビルドは未署名です。
最初はGitHubのソースアーカイブを提供するソースリリースにできます。
その場合、Release本文に「ソースのみ。APKは各自でビルド」と明記し、ビルド手順を案内します。
未署名APKをインストール用として添付しないでください。

APKを配布する場合は、継続して管理する専用の署名鍵、更新時の署名互換性、保管・復旧方法を決めます。
個人環境のdebug鍵を配布用の恒久鍵として流用せず、鍵をリポジトリに入れないでください。
署名・APK内容・対応端末・動作条件を確認してから、配布ファイルとチェックサムを用意します。

## 4. 公開し、外部から確認する

公開の承認後、検証済みコミットをpushし、そのコミットにタグを付けてGitHub Releaseを作成します。
Release本文には、変更点、導入方法、既知の制限、実機確認の範囲を記載します。
GitHub上のタグが候補コミットを指し、Release・本文・ソース・必要な添付ファイルを匿名で取得できることを確認します。
公開済みタグを別のコミットへ付け替えず、後続修正は新しい版にします。
GitHub Releaseの作成は、すべての実機条件を満たすという保証ではありません。
